CORRECTED MISCONCEPTIONS
==================================================
 
Historical misconceptions already corrected:
 
1. One EC2 instance automatically provides high availability.
 
2. AWS patches the EC2 guest operating system.
 
3. A managed service means AWS owns every responsibility.
 
4. Vertical scaling automatically equals elasticity.
 
5. Availability automatically equals redundancy.
 
6. Encryption automatically provides authorization.
 
7. Multiple EC2 instances automatically means Multi-AZ.

8. Source code that calls an AWS API directly possesses the IAM permission
   required for that API operation.

9. Long-lived access keys supplied directly to Lambda are the preferred
   workload-identity design.

10. The target role belongs in the caller role's trust policy when the
   caller wants to assume the target role.

11. Corporate access groups displayed through the AWS portal are AWS IAM
   groups.

12. Disabling a federated employee immediately invalidates every existing
   AWS temporary session.

13. Revoked credentials must be physically deleted or terminated.

14. An excessive role-chaining duration request is silently shortened to
   one hour.

15. A successfully issued Role B session expires when its source Role A
   session expires.

16. Original developer permissions directly grant or modify the target
   EngineeringRole.

17. Multiple ordinary identity-policy Allows are intersected.

18. An implicit deny in one identity policy overrides an Allow in another
   identity policy.

19. All permissions-boundary policies attached to a role are unioned.

20. A permissions boundary grants permissions independently.

21. SCPs restrict management-account IAM users and roles in the same way
   as member-account principals.

22. Least privilege is the authorization rule that denies a request when
   no Allow exists.

23. A same-account resource-policy grant to a role ARN fails only when the
   role identity policy lacks an Allow.

24. arn:aws:iam::<account-id>:root in Principal means only the human AWS
   account root user.

25. Trusting an AWS account automatically allows every identity in that
   account.

26. A particular S3 bucket ARN may be used directly as Principal when S3
   invokes Lambda.

27. An EventBridge rule ARN may be used directly as Principal when
   EventBridge invokes Lambda.

28. A failed condition in an Allow statement becomes an explicit Deny.

29. A Lambda policy broadly allowing EventBridge causes every EventBridge
   event to invoke the Lambda.

30. If SourceAccount matches, a different source resource in the same
   account may be allowed when SourceArn requires one exact resource.

31. Cross-account authorization operates as a literal handshake.

32. An app client ID may be a secret that securely proves an application's
   identity.

33. A trusted backend may safely hardcode its app-client secret in source
   code.

34. The backend verifies a JWT by comparing it with another stored token.

35. JWT header and payload decoding requires a key or secret.

36. An IAM role may have a resource-based policy attached to it instead of
   a trust policy.

37. An Identity Pool user directly assumes the Identity Pool.

38. Pre sign-up runs merely because the user clicked a frontend Sign up
   button.
 
Do not delete historical misconceptions.
 
Add new misconceptions when discovered.
